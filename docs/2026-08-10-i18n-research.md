# Internationalization implementation research

Research performed: 2026-08-10 10:20:41 CST (+0800).

Status: research and recommendation only. No internationalization implementation or translated user-facing content was added.

## Why this research was done

The requirement was to investigate how internationalization should be implemented in the Phi Help project. The research covered the current site architecture, VitePress 1.6.4 capabilities, the existing Phi product localization conventions, search and SEO behavior, deployment under `/help/`, and translation-maintenance options.

## Executive summary

The project is English-only today and has no i18n abstraction, locale configuration, translation catalog, or language negotiation.

The recommended implementation is:

1. Keep English at the existing root routes so all current URLs remain compatible.
2. Use VitePress's native file-based locales, with one complete Markdown tree per locale, for example `site/zh-Hans/...` publishing under `/help/zh-Hans/...`.
3. Keep long-form documentation as translated Markdown. Do not move documentation prose into runtime JSON catalogs or add i18next for page content.
4. Localize the VitePress shell through locale-specific `themeConfig`, local-search translations, and a small typed dictionary for the two custom Vue components.
5. Expose a locale only when its complete page set, navigation, metadata, custom UI, and search behavior have passed review. VitePress's default corresponding-page language switch can otherwise lead to a missing route.
6. Reuse the Phi terminology glossary and canonical locale identifiers as editorial inputs, but do not onboard the Help Markdown corpus into the current `phi-i18n` UI-string pipeline.

This approach preserves static rendering, search indexing, canonical URLs, sitemap generation, and the existing Cloudflare deployment. No new runtime dependency is required for the first implementation.

The largest cost is content, not code: the site contains 22 Markdown files and approximately 19,329 English words. The FAQ alone contains approximately 3,432 words. Translation review and ongoing source/translation synchronization therefore determine whether the solution is sustainable.

## Verified VitePress behavior

The following behavior was checked against the installed VitePress 1.6.4 source and a temporary two-locale production build using the same dependency:

- `locales.root` can represent the current English routes without moving any files.
- A locale key such as `zh-Hans` maps files under `site/zh-Hans/` to URLs under `/help/zh-Hans/`.
- Locale `lang`, title, description, and shallow-merged `themeConfig` values are applied to generated pages.
- VitePress generates a separate local-search index for each locale and only loads the active locale's index in the search UI.
- The generated sitemap groups matching relative page paths and emits reciprocal `xhtml:link` alternatives with each locale's `lang` value.
- The default language menu tries to preserve the current relative page path when switching languages.
- VitePress does not verify that the corresponding target page exists before producing that language-switch destination.
- VitePress does not redirect the root route based on browser language by default.

The temporary build produced both root and `zh-Hans` search indexes, correct `<html lang>` values, and reciprocal `hreflang` sitemap entries under the existing `/help/` base.

### Version-specific limitation

The current VitePress 1.6.4 `LocaleSpecificConfig` type supports locale-specific `lang`, `dir`, title, title template, description, head entries, and `themeConfig`. It does not include the newer per-locale `markdown` configuration shown in the current online VitePress documentation.

Do not rely on per-locale Markdown-renderer labels, such as code-copy text or default container labels, without either:

- upgrading VitePress and validating the new behavior, or
- supplying a project-owned override compatible with 1.6.4.

This site currently has only one fenced code block and its FAQ `details` titles are authored content rather than default container labels, so the limitation is small but visible.

## Recommended architecture

### URL and source layout

Keep English as the root locale and add language directories only for translations:

```text
site/
├── index.md
├── faq/index.md
├── memory/index.md
├── ...
├── zh-Hans/
│   ├── index.md
│   ├── faq/index.md
│   ├── memory/index.md
│   └── ...
└── .vitepress/
    ├── config.mts
    ├── i18n/
    │   ├── locales.ts
    │   └── theme-copy.ts
    └── theme/
```

Expected production URLs:

| Locale             | Home             | Example page            |
| ------------------ | ---------------- | ----------------------- |
| English            | `/help/`         | `/help/memory/`         |
| Simplified Chinese | `/help/zh-Hans/` | `/help/zh-Hans/memory/` |
| Japanese           | `/help/ja/`      | `/help/ja/memory/`      |

Keeping English at the root avoids redirects and preserves every existing link, canonical URL, analytics path, and external reference.

Use canonical Phi locale identifiers for locale keys and language tags:

- `en`
- `de`
- `es`
- `fr`
- `ja`
- `ko`
- `nl`
- `zh-Hans`
- `zh-Hant`

This matches the language model already used by Phi's macOS and Sidecar products. Chinese stays script-first: Simplified and Traditional are separate catalogs, and Traditional Chinese must not silently fall back to Simplified Chinese.

The current English content is explicitly global rather than US-only. Set the root locale to `lang: "en"` unless product or SEO ownership chooses US-specific targeting. The current implicit `en-US` value is not an intentional project decision.

### Content ownership

Treat English Markdown as the source content and each locale directory as a reviewed derivative.

Do not extract paragraphs into translation keys. Static translated Markdown preserves:

- natural document structure;
- headings and outlines;
- VitePress frontmatter;
- internal links;
- searchable rendered text;
- static HTML for crawlers and no-JavaScript users;
- straightforward editorial review in pull requests.

A runtime translation library would add indirection while weakening static SEO, author readability, local-search indexing, and Markdown link validation. It would also turn long-form editing into key management, which is not the credible change axis of this project.

### Navigation and theme copy

Use VitePress locale-specific `themeConfig` for:

- translated nav items;
- translated sidebars;
- outline labels;
- previous and next labels;
- appearance labels;
- mobile menu labels;
- language-menu accessibility text;
- skip-link accessibility text.

Keep shared mechanisms such as logo configuration, external links, social links, and search provider at the top level. Locale `themeConfig` is shallow-merged, so adding a locale-level `search` object would replace rather than deeply merge the shared search configuration.

A small helper may generate structurally identical sidebars from a locale prefix and translated labels. It should remain a config helper, not become a general-purpose i18n framework.

### Custom component copy

`CookieConsent.vue` and `PhiSidebarButton.vue` sit outside VitePress's built-in theme translations. Use a typed in-repository dictionary selected through VitePress `useData().localeIndex`.

Do not add i18next solely for these two components. Their copy is small, known at build time, and changes with this site rather than with an external service.

Cookie Consent needs additional governance:

- Its consent record is shared with the main marketing site, but the record contains decisions rather than copy and does not need a schema change.
- The translated category meanings must remain semantically identical to the main site's English consent UI.
- The privacy link is a raw `/privacy/` link and currently resolves to the main site's Privacy Policy, not the Help guide under `/help/privacy/`.
- The main marketing site's recorded SEO decision currently keeps localization out of scope.
- Privacy or legal ownership must approve translated consent and policy references before publication. Mechanical translation review is not sufficient.

### Internal links and anchors

Do not copy the current root-relative links unchanged into translated Markdown.

Use one enforced convention for non-root locale content:

- locale-relative links such as `../memory/` and `../privacy/#usage-statistics`, or
- explicit locale-prefixed links such as `/zh-Hans/memory/`.

Locale-relative links avoid embedding the current locale code throughout each translation and are the recommended default. A validation script should reject root-relative internal links inside non-root locale trees unless they are explicitly allowlisted as cross-locale links.

Translated headings produce translated slugs. For the 11 existing cross-page anchor links, either:

- translate and validate both the heading and its inbound link together, or
- assign stable explicit anchor IDs where VitePress supports them and where long-term inbound compatibility matters.

### Search

Keep VitePress local search initially. Its key benefits still apply: static build-time indexes, no query leakage, no external service, and one index per locale.

Search UI labels must be configured under `themeConfig.search.options.locales`.

CJK content needs a dedicated search-quality gate. The default whitespace-oriented MiniSearch behavior is not sufficient for Chinese and can be weak for Japanese. VitePress exposes MiniSearch `tokenize` and `processTerm` options but does not provide an official CJK tokenizer implementation. The installed 1.6.4 build applies one global MiniSearch tokenizer configuration while producing separate locale indexes.

Before launching a CJK locale, implement and test a multilingual tokenizer, likely based on `Intl.Segmenter` with a deterministic fallback, against representative queries from the actual Help content. If acceptable CJK results cannot be achieved without hurting Latin-language search, reconsider the search provider rather than shipping a non-functional search box.

Do not move to Algolia only because a second language exists. Revisit that choice if content reaches hundreds of pages, cross-site search becomes a requirement, or local CJK relevance cannot meet the agreed acceptance criteria.

## SEO and metadata

### What already works

The existing canonical function derives URLs from `pageData.relativePath`. A translated file such as `zh-Hans/memory/index.md` therefore naturally produces `https://phibrowser.com/help/zh-Hans/memory/` and remains self-canonical.

VitePress 1.6.4 automatically emits reciprocal sitemap alternatives for locale pages with matching relative paths. Google accepts sitemap `hreflang` annotations as an alternative to duplicate annotations in every HTML head.

### What needs adjustment

The project's sitemap policy functions currently compare route paths such as `/faq/` and `/what-is-phi-browser/` directly. A locale route such as `/zh-Hans/faq/` would miss the intended weekly frequency and priority rules. Normalize the locale prefix before applying page policy.

Add locale-aware social metadata:

- `og:locale` for the current locale;
- `og:locale:alternate` for available counterparts, if social-sharing requirements justify it.

Keep one self-referencing canonical per translated page. Do not canonicalize translated content to English, because that would suppress the localized page as an independent result.

Google recommends separate URLs, explicit language links, a single visible language per page, and no forced language redirect. The VitePress language picker satisfies the user-choice requirement. Retain `/help/` as the stable English fallback rather than redirecting automatically from browser language.

An `x-default` alternate is optional here because there is no language-selector gateway or forced redirect. If product ownership wants one, the English counterpart is the natural fallback and it must be added consistently.

## Deployment impact

No Cloudflare directory change should be required.

With the current configuration, a translated file under `site/zh-Hans/` is emitted under `site/.vitepress/dist/help/zh-Hans/`. Wrangler already serves the parent `site/.vitepress/dist/`, and upstream routing already forwards `/help/*` without stripping the prefix.

The deployment invariant remains:

```text
request /help/zh-Hans/memory/
→ asset root site/.vitepress/dist/
→ file help/zh-Hans/memory/index.html
```

Production verification is still required because a static build cannot prove upstream forwarding, caching, or content-type behavior.

## Relationship to Phi's shared translation pipeline

The company already has a separate UI-string pipeline across `phi-i18n-internal` and the public `phi-i18n` repository. It provides valuable conventions for Help:

- English is authoritative.
- Missing or stale translation is preferable to a wrong translation.
- Locale identifiers are canonical BCP 47 tags.
- Chinese is script-first with separate `zh-Hans` and `zh-Hant` content.
- Brand and product terminology should follow the ratified glossary.
- Machine-generated translation is a draft, not human approval.

The Help site should consume those conventions editorially, but should not currently join that pipeline:

1. The collector protocol is designed for discrete UI strings in WebExtension JSON, i18next JSON, or Apple string catalogs, not page-sized Markdown documents.
2. The public catalog is CC0, while Help content and its translated derivatives are licensed under CC BY-NC-SA 4.0. Publishing Help prose through that catalog would create a material licensing conflict.
3. The public repository still contains only smoke-test data, and the shared pipeline's fold, ingest, freshness checks, and Weblate community phase are not yet all operational according to its current runbook.
4. Flattening 19,329 words of connected prose into neutral string keys would lose document structure and make link, heading, and metadata maintenance harder.

If the company later deploys Weblate for documentation, use a separate Help component and preserve this repository's content license. Weblate's Markdown format can extract translatable content, but its current documentation marks Markdown support as under development, does not support translator descriptions or context, and treats Weblate rather than edited translation files as the translation source of truth. Pilot it on one page before adopting it as the editorial system.

## Options considered

| Option                                                       | Assessment                                                                                                 | Decision                                                            |
| ------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| VitePress native locale directories with translated Markdown | Preserves static pages, SEO, search, and authoring model; smallest architecture change                     | Recommended                                                         |
| Runtime i18next for all documentation                        | Adds keys and runtime coupling; poor fit for long-form Markdown and static indexing                        | Reject                                                              |
| One independent VitePress build per language                 | Strong isolation but duplicates configuration, deployment, sitemap, and theme maintenance                  | Defer unless locale release cycles must be independently deployable |
| Machine translation at request time                          | Non-deterministic, not statically searchable, costly, and unsuitable for reviewed product/privacy guidance | Reject                                                              |
| Put Help prose into the shared `phi-i18n` catalog            | Format and license mismatch; shared pipeline is not ready for long-form content                            | Reject for current scope                                            |
| Weblate Markdown workflow                                    | Potential future editorial tool, but current format support has important limitations                      | Pilot later, not a prerequisite                                     |

## Proposed implementation sequence

### Phase 0: product decisions

Before editing implementation, the owner must decide:

1. Which locale is the first pilot.
2. Whether a locale launches only at complete page parity or may launch partially.
3. Who owns translation review for product terminology, privacy, and legal consent copy.
4. Whether Help localization may launch while the main marketing site remains English-only.
5. Whether the root language should be generic `en` or intentionally target `en-US`.

Recommended default: one locale pilot, complete page parity before exposure, no automatic language redirect, and English retained at root.

### Phase 1: i18n-ready shell

- Add VitePress `locales` with English root and one approved pilot locale.
- Split locale-specific navigation and sidebar copy from shared config.
- Add search UI translations.
- Add the typed custom-component copy dictionary.
- Make sitemap policy and social metadata locale-aware.
- Add locale parity and link-escape validation.
- Keep translated locale routes unpublished until content and copy review are complete.

### Phase 2: pilot content

- Translate the 22-page tree and frontmatter.
- Apply the Phi glossary and keep-English brand rules.
- Repair locale-relative internal links and translated anchor targets.
- Validate local search with real queries, including CJK segmentation when applicable.
- Obtain independent product-copy review and privacy/legal review where required.

### Phase 3: publish and verify

- Run repository validation.
- Inspect generated language tags, canonical URLs, search indexes, and sitemap alternatives.
- Deploy to the production origin.
- Verify language switching, deep links, 404 behavior, assets, consent UI, analytics consent continuity, and search in a real browser.
- Submit or revalidate the sitemap in Google Search Console and monitor localized indexing.

### Phase 4: expand

Add locales one at a time using the same completeness and review gate. Reconsider translation-management tooling only after measuring source-change frequency, reviewer throughput, and translation drift during the pilot.

## Validation plan

### Automated

Use existing project commands:

```sh
pnpm format:check
pnpm build
```

Add focused checks for:

- identical route-file sets between English and every published locale;
- required translated frontmatter;
- no unintended root-English links from locale Markdown;
- translated navigation and custom-component key completeness;
- no missing internal links or anchors;
- expected `<html lang>` and self-canonical values in generated HTML;
- reciprocal sitemap language alternatives;
- one search index per locale;
- representative Latin and CJK search queries.

### Manual

For each published locale:

- Switch language from the home page and a deep page in both directions.
- Verify desktop and mobile navigation labels.
- Open search and test representative terms.
- Open Cookie Settings and Your Privacy Choices.
- Verify the shared consent decision survives navigation between the main site and Help.
- Verify the Ask Phi button label with Phi Browser and confirm that its extension contract is unchanged.
- Inspect a translated page's canonical URL, language tag, and social preview metadata.
- Confirm production `/help/<locale>/...` routing and trailing-slash behavior.

## Risks and mitigations

| Risk                                                   | Consequence                                             | Mitigation                                                                                       |
| ------------------------------------------------------ | ------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| Locale content falls behind English                    | Users receive stale or unsafe guidance                  | English-authoritative workflow, visible translation status, page-parity and source-change checks |
| Corresponding locale page is missing                   | Language switch leads to 404                            | Publish only complete locale trees, or implement an explicitly approved fallback router          |
| Root-relative links survive translation                | Readers silently return to English                      | Locale-relative link convention plus CI validation                                               |
| Translated heading changes an anchor                   | Deep links break                                        | Validate anchors or define stable IDs for durable cross-page targets                             |
| CJK search uses default tokenization                   | Search appears present but cannot find expected content | Real-query acceptance tests and custom tokenizer before launch                                   |
| Consent translation changes legal meaning              | Invalid or misleading consent                           | Privacy/legal review against final deployed copy                                                 |
| Help and main site language policies diverge           | Mixed-language journey and inconsistent consent UI      | Explicit product decision and cross-site QA before publication                                   |
| Machine drafts are treated as approved                 | Terminology and factual errors ship                     | Separate mechanical validation, product-copy review, and professional review where required      |
| Help content enters CC0 catalog                        | License incompatibility and loss of content controls    | Keep translated Markdown in this CC BY-NC-SA repository                                          |
| New online VitePress API is assumed available in 1.6.4 | Build or type failures                                  | Validate against installed package; upgrade only as a deliberate dependency change               |
